# Peer B minimum — explicit requests, waits and results (0.1.2)

Frozen before product edits, 2026-11-01. User authorized the proposed minimum B and version increment. Baseline: /private/tmp/dsh-peer-baseline-0.1.1-20261101. The existing A guard and card layout remain. No commit, publishing, real-profile installation, user Host restart, or C subscriptions.

## Contract and defaults

PB01 (implementation default, reversible; broader B remains proposed): add peer_request({requests:[{to,text}],wait?}), peer_reply({requestId,kind:question|answer|result,text,questionId?,wait?}), peer_wait({requestIds?}). The request/reply tools explicitly hand off this turn, wait defaults true; wait:false keeps local work running. Ordinary peer_send remains legacy and never concludes a turn. A batch includes all peers needed this turn (1–8 destinations); same-step other tools and fresh user steering are retained by the real Host. Only accepted handoffs call exec.concludeTurn(); failed/uncertain delivery must not conclude. A completed result is distinct from agent idleness or a transport receipt.

PB02: request IDs are generated by the runtime, scoped to requester, responder and Host incarnation. One unresolved outgoing request per direction; different peers may run concurrently. A second request to that peer is explicitly rejected as request-pending, its new text is not silently dropped. A result releases that slot only after its user/message event is consumed in the requester session, never on queue admission; delivery and consumption are recorded separately. Questions/answers remain under the same request and require a matching runtime question ID. Up to 3 clarification rounds per request. A result closes the request once; identical repeats return the recorded receipt without delivery, changed/late results are rejected. Pending and queued-result states are observable without polling the other agent.

PB03: bounded volatile state, at most 512 request records per Host, 10-minute lifetime; expired/completed records are not replayed. Restart invalidates outstanding requests (explicit stale/unknown response), no persistence/resumption guarantee. No claim of a trusted user-root budget across arbitrary nested requests; A's directional limits still apply. Monotonic local expiry; Host incarnation prevents old wire messages entering a restarted instance. Capacity failure never evicts an active record. Structured mode can be disabled by Host config `requests:false`.

PB04: capability `request-result-v1` on registry records, and dedicated `exchange` wire type within the existing v1 transport. Both peers must advertise support and current incarnation. Old endpoints return unsupported; no silent conversion to legacy text. Token, liveness, byte limits, atomic reserve/commit/rollback and directional A counters are reused. Content dedup includes request/kind/question identity so equal answers to distinct requests are not suppressed. Successful queued delivery updates local lifecycle before a reentrant callback; failed admission rolls back. Unknown acknowledgements retain uncertainty, never auto-resend.

PB05: structured envelopes give exact request/question IDs, current pending/queued state and concise rules. Encourage only new findings/changes and final conclusions, without arbitrary truncation of substantive content. Old relay text stays unchanged. Display v2 identifies structured envelopes; v1 and legacy history remain readable. Received titles stay `来自 @reviewer · first line`; body excludes that line. Tool cards display actual handoff/result/wait state, without a permanent pause banner. Model request fields and payloads remain visible in raw details.

PB06 (pre-implementation review clarification): request batches conclude only when every item is accepted; each accepted/failed/uncertain receipt is retained, accepted items are never rolled back or resent. An uncertain item retains its direction slot. question is responder-only, answer requester-only with the current runtime questionId, result responder-only and forbidden while an unanswered question exists. Identical final retries return the saved receipt; other out-of-order replies fail. Lifetime starts at local record admission and completed receipts remain until that original deadline; reclaimed IDs return unknown-request.

PB07 (original, superseded by PB08 after batch-2zMCau): peer_wait without IDs selects this session's active incoming/outgoing records; an explicit empty list is a no-op. Unknown/expired/not-owned IDs fail with wait:false. No active record means wait:false (not a claim that the user task is finished). A queued question/result/answer returns wait:false and its state, so the caller cannot mistake queued for finished. Awaiting remote work/answer can hand off with wait:true. Final results close responder work immediately; requester results remain queued until consumption. Mixed queued and pending returns wait:false with both states. The real Host must drain queued messages independently of terminal tool steps.

PB08 (fixed before the follow-up batch, unchanged model thresholds): actual E06 and a real Host red test show that queued inputs require yielding the current turn. peer_wait may conclude if each selected active record either has an unconsumed queued message or is pending/awaiting-answer. Consumed working/question records require local action and prevent handoff, including mixed sets. Empty/unknown/expired/not-owned behavior stays unchanged. Handoff never clears a slot; result consumption still does. Message instructions are kind/role specific: result recipients must not reply to a closed ID; a next review round uses a new request with explicit to in every item. Request/answer recipients finish with result or clarify with question; question recipients answer its questionId. Concise tool instructions remove redundant background but never truncate task content. Malformed acknowledgements retain uncertainty just like a lost ACK.

PB09 (fixed before the next full batch, unchanged thresholds): peer_request additionally accepts a single explicit destination as {to,text,wait?}. It is mutually exclusive with {requests,wait?}; mixing forms, missing fields or an empty batch fails before admission and cannot conclude. No destination is guessed. Every valid batch retains its existing partial-business-failure receipts and all-success handoff rule. A single request counts one send attempt. Tool text instructions use concise incremental bullet points by default, while retaining task-required evidence and details; no hard truncation or scoring-specific content rule is introduced. Result envelopes name the explicit destination for a next round.

PB10 (frozen after batch-mGmdBW, before implementation and next full run): reduce repeated model-context overhead without removing original task/result text. peer_list defaults to names and status; details:true retains its full table, and /peers stays full. Compact tool descriptions retain legal roles, handoff semantics and legacy guard rules. Receipts preserve per-target accepted/failed/uncertain states, errors and request/question IDs. Envelopes preserve current IDs and role-specific actions; other pending work is summarized by name/state while peer_wait and original request receipts retain model-visible IDs. Request text follows the user's scope instead of inventing extra deliverables; necessary detail remains allowed. No hard content truncation, new scoring exception or budget change.

PB11 (frozen after complete batch-wLlLMb, before next run): a continuation to a peer with existing context should send new decisions/changes rather than restating that context, while supplying any missing necessary information. Final delivery follows the user's requested scope: summarize actual conclusions, unresolved items and necessary evidence; do not present suggestions as implemented fixes or restate the communication history/full existing plan unless the user needs that complete artifact. No hard length limit, truncation, case-specific rule or grading change. Restore the model-visible batch limit of eight.

PB12 (frozen after complete batch-0J80dh, before implementation): register a conditional dsh-peer:policy section through the public optional SystemPrompt service at TEAM_POLICY order, as the installed official Team plugin does. Never set complete or replace persona; allow authorized delegation while preventing peer messages from expanding/overriding original user scope. Preserve necessary user-requested detail. Host config promptPolicy:false disables this optional section. Existing complete personas may suppress ordinary sections; deterministic protection/tool rules remain. A real Host red test first proves the section is absent; the green test must prove the exact product policy reaches real model inputs. The evaluator collects only sections actually registered by each version's index.apply, with their conditions/order and all content counted in tokens; the scenario strings, limits and grading are unchanged. No evaluator-only wording or automatic peer-list disclosure is added.

## Risks and status

One outstanding request per direction and volatile restart behavior are deliberate minimum-B limits, not full orchestration. Prompt compliance alone does not guarantee zero semantic retries. Shorter envelopes must not break old display validation. Never conclude a failed handoff or swallow unrelated user input. Current status: 0.1.2 implementation and deterministic/real Host/browser validation complete; fixed model batch-SiC278 complete, changed 30/30 with unchanged thresholds and zero rejection/budget exhaustion. This establishes fixed-regression acceptance; broader root budgets, persisted recovery and subscriptions remain outside scope. Independent review findings and red/green evidence are recorded in acceptance.md.
